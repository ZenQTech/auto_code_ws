## 1. 项目概述

### 1.1 项目定位

本项目构建一个**机器人全栈自动化编程多智能体协同平台**（以下简称「智能体调度平台」），作为 Claude Code CLI 的全局唯一调度中枢，通过多智能体协同架构，自动完成从模糊需求输入到可交付代码的机器人软件开发全流程。

### 1.2 核心目标

| 目标 | 描述 | 成功度量 |
|------|------|---------|
| **自动化编程流水线** | 实现「需求输入 → 代码交付」的全流程自动化，覆盖需求澄清、架构设计、批判迭代、任务拆解、协同开发、集成评测、仿真验证、交付归档 8 个核心阶段 | 全流程无人干预完成率 ≥ 90% |
| **多智能体协同** | 基于 Claude Code CLI 实例池，按任务类型自动匹配最优智能体角色，支持并行开发与串行依赖管控 | 并行任务利用率 ≥ 80% |
| **配额成本管控** | 全流程 API 调用次数与 Token 消耗实时监控，三级告警与熔断机制，确保在 Coding Plan Pro 配额内最大化产出 | 配额超支事件 = 0 |
| **安全质量保障** | 全链路安全编码规范、高风险模块强制人工审核、多层级校验机制，确保机器人代码的安全性与可靠性 | 致命安全缺陷漏检率 = 0 |

### 1.3 运行环境

| 维度 | 规格 |
|------|------|
| 后端框架 | Python 3.10+ / FastAPI |
| 数据库 | SQLite 3 + SQLAlchemy 2.0（异步，WAL 模式） |
| 前端框架 | React 18 + TypeScript + Vite 6 + TailwindCSS 3 |
| AI 执行单元 | Claude Code CLI（通过 `claude` 命令调用） |
| AI 调度器 | Hermes CLI（通过 `hermes` 命令调用，可选） |
| AI 模型 | 火山引擎 Coding Plan API（deepseek-v4-pro 主模型 / deepseek-v4-flash 备用模型） |
| WebSocket | websockets 14.1 + FastAPI |
| 版本管理 | Git + GitPython 3.1.43 |
| 操作系统 | Ubuntu 22.04 LTS |

### 1.4 目标用户与使用场景

| 用户角色 | 典型场景 | 核心诉求 |
|---------|---------|---------|
| 机器人软件开发工程师 | 快速从需求到代码的全流程自动化 | 减少重复编码工作，聚焦核心算法 |
| 自动化系统集成工程师 | 多模块协同开发与集成校验 | 模块间接口一致性保障，集成测试自动化 |

#### F-1: 顶层调度中心（全局唯一调度中枢）

**职责**：作为平台的唯一 API 调用入口与全流程状态管控核心，负责本地拦截调度、顶层任务调度、心跳进度跟踪、状态维护反馈、异常兜底、本地校验执行、数据持久化、Git 版本管理。

**核心能力**：

| 能力项 | 描述 | 输入 | 输出 |
|--------|------|------|------|
| 需求理解与引导 | 多轮引导用户补充开发关键细节（约束条件、性能指标、仿真环境、安全红线、ROS/依赖版本） | 用户模糊需求描述 | 结构化需求文档（待确认） |
| 提示词优化 | 对多轮用户提示词进行标准化优化，消除语义歧义，固化核心约束 | 用户确认的需求文档 | 标准化提示词 |
| 任务分发 | 按照任务模块生成多个 Claude Code CLI 实例，注入标准化提示词 | 标准化任务清单 | Claude Code CLI 实例池 |
| 原子任务聚合 | 阅读所有 CLI 实例生成的 plan/checklist/task 文档，整合为统一原子任务清单 | 各 CLI 实例的任务规划文档 | 统一原子任务清单 |
| 高风险标记 | 严格按照高安全风险模块三级界定标准，精准标记风险等级 | 原子任务清单 | 带风险标记的任务清单 |
| 全局配置管理 | 维护全流程可配置参数，支持用户自定义调整 | 用户配置修改 | 更新后的全局配置 |
| 双重心跳检测 | 实时检测 Claude Code 运行状态、单任务执行状态、Hook 打点有效性 | Hook 事件 + 主动轮询 | 心跳状态报告 |
| 进度同步 | 接收 Claude Code Hook 通知，同步任务进度、完成状态、告警信息 | Hook 通知 | 更新的任务状态 |
| 全流程校验 | 静态检查、安全编码校验、预编译校验、测试脚本执行结果确认 | 代码产物 | 校验结果（通过/打回） |
| 系统评测 | 全量代码全局深度评测、全链路实时性评测、核心算法专项评测、安全专项评测 | 集成后的全量代码 | 结构化评测报告 |
| 断点续跑 | 任务中断后自动恢复，从最近完成节点重启 | 中断状态 | 恢复后的执行状态 |
| 记忆库管理 | 调用 Hermes 智能体完成 Skill 编写与入库 | 任务完成记录 | Skill 入库确认 |

**状态管理模型**：

调度中心维护以下全局状态，所有状态变更必须原子化写入数据库：

```
全局状态机：
  IDLE         → 等待用户输入
  CLARIFYING   → 需求澄清中（F-2 激活）
  ARCHITECTING → 架构设计/批判迭代中（F-3 激活）
  PLANNING     → 任务拆解与分发中（F-4 激活）
  DEVELOPING   → Agent Teams 协同开发中（F-5/6/7 激活）
  REVIEWING    → 全局校验/评测/安全审核中（F-11/12 激活）
  DELIVERING   → 交付归档中（F-14 激活）
  PAUSED       → 暂停（配额熔断/人工中断/异常）
  ERROR        → 异常终止（需人工介入）

状态转换规则：
  IDLE → CLARIFYING（用户提交需求）
  CLARIFYING → ARCHITECTING（需求确认）/ IDLE（用户取消）
  ARCHITECTING → PLANNING（架构确认）/ PAUSED（人工驳回超限）
  PLANNING → DEVELOPING（任务分发完成）/ ARCHITECTING（循环依赖打回）
  DEVELOPING → REVIEWING（全模块完成）/ PAUSED（配额熔断/异常）
  REVIEWING → DEVELOPING（评测不通过打回）/ DELIVERING（评测通过）
  DELIVERING → IDLE（交付完成）
  任意状态 → PAUSED（配额熔断/人工暂停）
  任意状态 → ERROR（不可恢复异常）
  PAUSED → 上一状态（恢复）/ ERROR（超时未恢复）
```

**边界条件与异常处理**：

| 场景 | 处理策略 | 恢复方式 |
|------|---------|---------|
| Hook 通知丢失 | 双重超时检测 + 主动状态轮询，超过预期执行时间 2 倍未收到 Hook 打点，主动查询 Claude Code 任务状态 | 自动 |
| 调度中心进程崩溃 | 重启后从 SQLite 数据库恢复状态，执行全量一致性校验（产物完整性、全局信息变更、依赖链一致性） | 自动 |
| 所有 CLI 实例均不可用 | 触发全局告警，暂停任务分发，等待 CLI 恢复或人工介入 | 人工 |
| 数据库写入失败 | 重试 1 次；连续 3 次失败触发告警，自动降级写入本地临时 JSON 文件 | 自动降级 |
| 状态机非法转换 | 拒绝操作，记录告警日志，返回当前合法状态列表 | 自动拒绝 |
| 并发状态冲突 | 乐观锁 + 版本号机制，冲突时以后写入者为准并记录告警 | 自动 |

#### F-2: 需求澄清与确认模块

**职责**：将用户模糊的开发构想转化为结构化、无歧义的需求文档。

**核心能力**：

- AI 引导用户补充完整机器人开发关键细节
- 约束条件、性能指标、仿真环境要求、安全红线要求、ROS/依赖版本信息的结构化采集
- 输出标准化结构化需求文档（3 个固定章节：项目核心需求概述、结构化需求详情、待确认补充事项）
- 多轮交互直到需求明确，支持用户确认/驳回
- 需求变更时同步更新需求文档，明确变更影响范围

**交互流程**：

```
用户输入模糊需求
    ↓
[智能体调度平台] 分析需求模糊度，生成补充提问清单
    │  ├─ 分类：项目类型 / 技术栈 / 性能指标 / 安全要求 / 环境约束
    │  └─ 每类最多 3 个问题，总计不超过 10 个问题
    ↓
用户补充关键细节
    ↓
[智能体调度平台] 评估需求完整度
    ├─ 完整度 ≥ 80% → 生成结构化需求文档
    └─ 完整度 < 80% → 继续补充提问（最多 5 轮）
    ↓
[智能体调度平台] 生成结构化需求文档
    ├─ 章节 1: 项目核心需求概述
    ├─ 章节 2: 结构化需求详情
    └─ 章节 3: 待确认补充事项
    ↓
用户确认
    ├─ 通过 → 进入架构设计阶段（F-3）
    └─ 不通过 → 标注驳回原因 → 继续补充优化（最多 3 轮驳回）
```

**输出规范**：

| 章节 | 内容要求 | 必填项 |
|------|---------|--------|
| 项目核心需求概述 | 核心目标、应用场景、功能边界、仿真环境要求、安全红线、版本约束 | 全部 |
| 结构化需求详情 | 分模块功能需求、性能指标、环境约束、技术栈要求、安全要求、验收标准 | 全部 |
| 待确认补充事项 | 模糊/缺失信息的补充提问清单 | 若有缺失则必填 |

**边界条件**：

| 场景 | 处理策略 |
|------|---------|
| 用户需求过于模糊（如"做一个机器人"） | 不少于 5 轮引导交互，覆盖项目类型、ROS 版本、仿真环境、安全要求、核心功能 |
| 用户中途放弃需求澄清 | 保存当前对话状态至数据库，支持后续恢复继续 |
| 需求包含明显矛盾（如"高精度"但要求"低成本传感器"） | 主动指出矛盾，引导用户明确优先级，记录矛盾点 |
| 用户连续驳回 3 次 | 触发人工介入提示，建议用户重新梳理需求 |
| 需求澄清超时（24h 无响应） | 保存状态，标记为「待恢复」，推送提醒 |

#### F-3: 架构设计与批判迭代模块

**职责**：基于确认的需求文档，生成系统架构设计，并通过批判迭代确保架构质量。

**核心流程**：

```
确认的需求文档
    ↓
[总架构师智能体] 生成初始架构设计
    输出: 5 章节架构文档（系统整体架构、模块职责与接口规范、
          核心技术方案与算法选型、技术栈与环境约束、系统验收标准）
    ↓
[批判反思智能体] 全维度架构批判
    输出: 结构化缺陷清单（含缺陷等级、影响范围、修复建议）
    ↓
[总架构师智能体] 架构迭代优化
    输入: 上一版架构 + 缺陷清单
    输出: 优化后的架构设计
    ↓
[迭代次数 < 3?]
    ├─ 是 → 继续批判迭代
    └─ 否 → 强制进入人工确认
    ↓
人工架构确认
    ├─ 通过 → 进入任务拆解阶段（F-4）
    └─ 驳回 → 重新走批判迭代流程（最多 2 次驳回）
```

**刚性规则**：

| 规则 | 阈值 | 超限处理 |
|------|------|---------|
| 架构批判迭代次数 | ≤ 3 次 | 强制进入人工确认 |
| 人工驳回次数 | ≤ 2 次 | 强制触发人工评审，输出历史驳回记录与缺陷清单 |
| 人工驳回后流程 | 必须重新走批判迭代 | 禁止跳过批判环节直接提交 |

**架构设计输出规范（5 章节）**：

| 章节 | 必须包含内容 |
|------|-------------|
| 系统整体架构 | 分层架构图、模块划分、数据流、控制流 |
| 模块职责与接口规范 | 每个模块的职责描述、输入/输出接口、依赖关系 |
| 核心技术方案与算法选型 | 算法选型理由、复杂度分析、备选方案对比 |
| 技术栈与环境约束 | 编程语言、框架版本、ROS 版本、硬件约束、网络约束 |
| 系统验收标准 | 功能验收项、性能指标、安全标准、测试方法 |

**边界条件**：

| 场景 | 处理策略 |
|------|---------|
| 批判未发现任何缺陷 | 直接进入人工确认，不强制迭代 |
| 架构描述存在歧义 | 触发提示词工程智能体进行结构化优化 |
| 人工确认超时（24h） | 触发告警，暂停依赖该节点的任务，7 天未处理自动标记为「暂停状态」 |
| 批判结果与上一轮完全一致（无新缺陷） | 视为收敛，自动进入人工确认 |
| 需求文档被修改（架构设计进行中） | 暂停架构设计，重新评估影响范围 |

#### F-4: 任务拆解与分发模块

**职责**：基于确认的架构，生成标准化任务清单，完成前置校验后分发至 Claude Code Agent Teams。

**核心流程**：

```
确认的架构设计
    ↓
[架构拆解与任务规划智能体] 生成标准化 JSON 任务清单
    含：依赖关系、风险等级、优先级、超时时间
    ↓
[任务清单复核]
    ├─ 风险等级准确性校验
    ├─ 依赖关系合理性校验
    └─ ★ 拓扑排序循环依赖检测（Kahn 算法，O(V+E)）
    ↓
[复核通过?]
    ├─ 不通过 → 打回架构拆解智能体修正
    └─ 通过 ↓
[最终前置校验]
    ├─ 依赖存在性校验（依赖的 task_id 是否真实存在）
    ├─ 模型白名单校验（指定的 adapt_model 是否可用）
    ├─ 验收标准明确性校验（是否可量化）
    └─ 超时合规性校验（是否在类型超时上限内）
    ↓
[前置校验通过?]
    ├─ 不通过 → 触发重写
    └─ 通过 ↓
[顶层调度中心] 通过 Claude Code SDK 分发至 Agent Teams
    ↓
[启动] 心跳检测、配额监控、状态同步
```

**核心算法——拓扑排序循环依赖检测**：

> ⚠️ **架构批判修复 #3**：此算法在 v1.0 中未在模块职责中体现，v2.0 显式定义。
>
> **实现位置**：`backend/app/services/task_decomposer.py` → `TaskDecomposer._detect_circular_dependencies()`

| 检测类型 | 执行时机 | 算法 | 处理策略 |
|---------|---------|------|---------|
| **静态循环依赖检测** | 任务清单分发前 | Kahn 算法（拓扑排序），复杂度 O(V+E) | 存在循环依赖 → 打回架构拆解智能体修正依赖关系，禁止流入调度环节 |
| **隐式循环依赖检测** | 集成校验环节 | 基于 ROS 包依赖、头文件引用、服务调用关系扫描 | 发现隐式循环依赖 → 输出问题清单，触发对应模块修改 |
| **动态死锁检测** | 任务调度过程中 | 实时监控任务等待状态，检测交叉依赖与死锁 | 任务等待超自身超时 50% → 主动检查依赖任务状态；发现死锁 → 暂停所有相关任务，推送告警 |

**依赖有效性校验**：除循环依赖外，必须校验依赖的 task_id 是否真实存在，避免依赖不存在的任务导致永久停滞。

#### F-5: Claude Code Agent Teams 协同开发模块

**职责**：基于任务清单的依赖关系，协调多个 Claude Code CLI 实例进行协同开发。

**核心流程**：

```
任务清单分发
    ↓
[优先] 执行全局接口/消息定义任务（最高优先级）
    ↓
接口编译校验通过 → 下游任务可启动
    │
    ├─ 接口有变更 → 触发全局接口变更闭环 SOP（见 F-17）
    │
    ↓
[基于强依赖关系] 通过 Hook 有序触发各 Agent 执行
    ↓
[无前置依赖的任务] 按并行管控规则并行执行
    ↓
[核心算法/ROS 节点 C++ 代码完成] → 自动触发 C++ 性能优化
    ↓
[单模块代码完成] → 触发算法边界与安全校验
    ↓
[校验通过] → 触发测试脚本生成 → 执行测试 → Git 提交
    ↓
循环执行直到所有模块完成
```

**任务状态机**（6 种固定状态）：

```
                    ┌─────────┐
                    │ 待执行   │
                    └────┬────┘
                         │ 分配 Agent
                    ┌────▼────┐
            ┌───────│ 执行中   │◄──────────────┐
            │       └────┬────┘                │
            │            │                     │
     ┌──────┴──┐    ┌────┴────┐          ┌────┴────┐
     │ 已完成   │    │ 已失败   │──────────►│ 待更新   │
     └─────────┘    └────┬────┘          └─────────┘
                         │
                    ┌────┴────┐
                    │ 已阻塞   │（等待人工介入）
                    └─────────┘
```

**状态转换规则**：

| 当前状态 | 触发事件 | 目标状态 | 条件 |
|---------|---------|---------|------|
| 待执行 | Agent 分配成功 | 执行中 | 依赖任务全部完成 |
| 执行中 | 任务完成 + Hook 确认 | 已完成 | 产物校验通过 |
| 执行中 | 任务执行失败 | 已失败 | 自动重试 1 次后仍失败 |
| 执行中 | 前置任务变更 | 待更新 | 依赖的上游任务被修改 |
| 执行中 | 需要人工决策 | 已阻塞 | 高风险模块需人工审核 |
| 已失败 | 代码修复完成 | 待更新 | 修复后重新进入队列 |
| 待更新 | 更新完成 | 执行中 | 重新分配 Agent |
| 已阻塞 | 人工确认通过 | 执行中 | 人工解除阻塞 |
| 已阻塞 | 人工驳回 | 已失败 | 需重新修改 |

**刚性规则**：

| 规则 | 说明 |
|------|------|
| 状态变更必须通过 Hook 同步打点 | 禁止跳过 Hook 直接修改状态 |
| 未完成任务禁止下游 Agent 启动 | 严格遵守依赖关系 |
| 任务失败/阻塞/待更新时 | 立即暂停下游所有依赖任务 |
| 单任务代码修改/测试迭代 | 最多 3 次，超过阈值触发人工审核 |

**并行管控规则**：

| 配额告警等级 | 最大并行任务数 | 单分钟最大调用次数 |
|-------------|--------------|------------------|
| 无告警（配额充足） | 5 个 | ≤ 20 次 |
| 一级告警 | 3 个 | ≤ 15 次 |
| 二级告警 | 2 个 | ≤ 10 次 |
| 三级告警/预留配额 | 1 个 | ≤ 5 次 |

**异常隔离机制**：单个并行任务出现超时、失败、阻塞异常，仅暂停该任务及其下游依赖任务，不影响其他无依赖的并行任务执行。

#### F-6: 三级执行策略路由模块

**职责**：根据任务复杂度自动选择最优执行模式，实现 **三级执行策略路由算法**。

> ⚠️ **架构批判修复 #1**：此算法在 v1.0 中未在模块职责中体现，v2.0 显式定义完整规格。
>
> **实现位置**：`cli_integration/strategy_router.py` → `StrategyRouter` 类

**核心算法——三级执行策略路由**：

```
任务输入
    ↓
复杂度估算（任务描述长度 + 关键词加权）
    ↓
计算复杂度评分（0.0 - 1.0）
    ↓
┌─ 评分 ≤ 0.3 → DIRECT 模式（--print 非交互式输出）
├─ 0.3 < 评分 ≤ 0.7 → SUBAGENT 模式（Task 工具拆分子任务）
└─ 评分 > 0.7 → AGENT_TEAM 模式（多类型 Subagent 协作）
```

| 复杂度评分 | 执行模式 | 适用场景 | 说明 |
|-----------|---------|---------|------|
| 0.0 – 0.3 | DIRECT（直接执行） | 简单工具函数、数据预处理、轻量 bug 修复 | 使用 `--print` 模式非交互式输出，最小化 Token 消耗 |
| 0.3 – 0.7 | SUBAGENT（子智能体） | 中等复杂度模块、单文件编码 | 使用 Task 工具拆分为子任务执行，支持内部迭代 |
| 0.7 – 1.0 | AGENT_TEAM（智能体团队） | 核心算法开发、架构设计、系统评测 | 启动多类型 Subagent 协作模式，支持角色分工 |

**复杂度估算维度**：

| 维度 | 权重 | 说明 |
|------|------|------|
| 任务描述长度 | 基础权重 | 按字符数归一化，上限 5000 字符 |
| 高复杂度关键词 | 高权重 (×3) | 系统、架构、分布式、安全、实时、核心算法、多线程、调度、评测 |
| 中复杂度关键词 | 中权重 (×2) | 接口、API、组件、模块、封装、集成、校验、测试 |
| 低复杂度关键词 | 低权重 (×1) | 工具、脚本、辅助、格式、文档、注释 |

**边界条件**：

| 场景 | 处理策略 |
|------|---------|
| 复杂度评分恰好位于阈值边界（0.3 或 0.7） | 向上取整（即 0.3 → SUBAGENT，0.7 → AGENT_TEAM），宁严勿松 |
| 无法估算复杂度（空任务描述） | 默认使用 DIRECT 模式，并记录警告日志 |
| 执行模式与任务类型不匹配 | 允许人工覆盖，通过配置调整执行模式 |
| 任务描述包含多种复杂度关键词混合 | 取最高权重关键词决定基准，再叠加其他关键词加权 |

#### F-7: 最少负载调度模块

**职责**：将任务合理分配给可用的 Claude Code CLI 实例，实现 **最少负载调度算法**。

> ⚠️ **架构批判修复 #2**：此算法在 v1.0 中未在模块职责中体现，v2.0 显式定义完整规格。
>
> **实现位置**：`backend/app/services/scheduler.py` → `TaskScheduler` 类

**核心算法——最少负载调度**：

```
待分配任务
    ↓
[获取] 所有可用 Agent 实例及其当前任务数
    ↓
[选择] 当前任务数最少的 Agent：min(agents, key=lambda a: a.current_tasks)
    ↓
[分配] 任务 → 更新 Agent 负载计数（+1）
    ↓
[任务完成] → 释放 Agent 负载计数（-1）
```

**调度策略**（可配置，`config/auto_code_config.yaml` → `scheduling.strategy`）：

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| **least_loaded**（默认） | 选择当前任务数最少的 Agent | 通用场景，最大化负载均衡 |
| round_robin | 轮询分配 | 任务复杂度均等的场景 |
| random | 随机分配 | 测试/调试场景 |
| manual | 手动指派到指定 Agent | 特殊任务需要特定 Agent 执行 |

**附加能力**：

| 能力 | 说明 |
|------|------|
| 优先级调度 | 高/中/低优先级调度，配额紧张时自动暂停低优先级任务 |
| 防任务饿死 | 低优先级任务等待超 24 小时临时提权，避免永久停滞 |
| 异常隔离 | 单个并行任务异常不影响其他无依赖的并行任务 |
| 负载监控 | 实时展示各 Agent 的 CPU/内存/任务数负载 |

**边界条件**：

| 场景 | 处理策略 |
|------|---------|
| 所有 Agent 均不可用 | 任务进入等待队列，Agent 恢复后自动分配 |
| Agent 在执行中崩溃 | 任务自动重新分配给其他可用 Agent，原 Agent 标记为异常 |
| 所有 Agent 负载均衡（任务数相同） | 优先选择空闲时间最长的 Agent |
| 手动指派 Agent 不存在 | 拒绝分配，返回错误提示 |
| 新 Agent 加入集群 | 自动纳入调度池，触发负载再均衡检查 |

#### F-9: 上下文生命周期管理模块

**职责**：管控所有 Agent 的对话上下文，防止上下文溢出导致输出质量下降。

**核心机制**：

| 能力 | 说明 |
|------|------|
| 上下文中区分 | 区分全局约束（固化信息）与对话信息（动态信息） |
| 压缩触发阈值 | 上下文达到 70%（200,000 Token 上限的 70% = 140,000 Token）时触发压缩 |
| 压缩策略 | 保留全局约束 + 最新对话 + 关键产物摘要，压缩中间冗余内容 |
| 调用失败处理 | 失败后指数退避重试，最多 1 次；连续失败切换备用模型 |
| 会话失效兜底 | Claude Code 会话失效时自动创建新会话，从数据库恢复上下文 |

**压缩策略详细说明**：

```
原始上下文（200K Token 上限）
    │
    ├─ 全局约束层（不可压缩）: ~20K Token
    │   └─ 项目需求、架构设计、接口规范、安全红线、编码规范
    │
    ├─ 关键产物层（摘要保留）: ~30K Token
    │   └─ 已完成任务的输出摘要、关键决策记录、接口定义
    │
    ├─ 最新对话层（完整保留）: ~50K Token
    │   └─ 最近 3 轮对话的完整内容
    │
    └─ 中间冗余层（压缩）: 剩余 Token
        └─ 早期对话的详细内容 → 压缩为摘要
```

**边界条件**：

| 场景 | 处理策略 |
|------|---------|
| 压缩后上下文仍超过阈值 | 进一步精简，仅保留全局约束 + 当前任务的核心上下文 |
| 压缩过程中 Agent 仍在执行 | 等待当前任务完成后执行压缩，避免中断 |
| 上下文压缩导致关键信息丢失 | 压缩后执行完整性校验，确保全局约束未丢失 |
| 会话 Token 即将耗尽（>95%） | 强制压缩，即使 Agent 正在执行也暂停并压缩 |

**职责**：在表现层（API 网关层）提供完整的认证与授权机制，防止未授权访问。

**核心能力**：

| **访问频率限制** | IP/用户维度的 API 调用频率限制 | 基于令牌桶算法，防止恶意调用与配额盗用 |
| **审计日志** | 所有 API 调用的完整审计记录 | 包含调用者、时间、操作、结果、IP 地址 |

**角色权限矩阵**：

| 操作 | 管理员 | 开发者 | 只读用户 |
|------|--------|--------|---------|
| 查看项目状态 | ✅ | ✅ | ✅ |
| 提交开发需求 | ✅ | ✅ | ❌ |
| 修改全局配置 | ✅ | ❌ | ❌ |
| 手动终止任务 | ✅ | ✅ | ❌ |
| 人工审核通过/驳回 | ✅ | ✅ | ❌ |
| 管理用户权限 | ✅ | ❌ | ❌ |
| 查看审计日志 | ✅ | ❌ | ❌ |
| 管理 API Token | ✅ | ❌ | ❌ |

**安全策略**：

| 策略 | 配置 | 说明 |
|------|------|------|
| Token 有效期 | 默认 24 小时 | 支持全局配置调整 |
| Token 刷新 | 有效期过半时可刷新 | 无需重新登录 |
| 敏感操作二次验证 | 配置修改、手动任务终止 | 需输入密码确认 |
| 账号锁定 | 连续认证失败 5 次 | 锁定 30 分钟，自动解锁 |
| 会话管理 | 单一会话模式 | 同一账号新登录踢出旧会话 |

**认证流程**：

```
[前端] 用户输入用户名/密码
    ↓
[POST /api/auth/login] 验证凭据
    ├─ 成功 → 返回 access_token + refresh_token
    └─ 失败 → 返回 401，记录失败次数
    ↓
[前端] 存储 token 至 localStorage，后续请求携带 Authorization: Bearer <token>
    ↓
[API 中间件] 每个请求验证 token
    ├─ 有效 → 解析用户角色，注入请求上下文
    ├─ 过期 → 返回 401，前端自动跳转登录
    ├─ 篡改 → 返回 401，记录安全告警
    └─ 权限不足 → 返回 403，明确提示所需权限
    ↓
[POST /api/auth/refresh] token 刷新
    ├─ refresh_token 有效 → 返回新 access_token
    └─ refresh_token 过期 → 返回 401，需重新登录
```

**边界条件**：

| 场景 | 处理策略 | HTTP 状态码 |
|------|---------|------------|
| Token 过期 | 返回 401，前端自动跳转登录页 | 401 |
| Token 被篡改 | 签名验证失败，返回 401，记录安全告警 | 401 |
| 权限不足 | 返回 403，明确提示所需权限级别 | 403 |
| 频率限制触发 | 返回 429，包含 Retry-After 头部 | 429 |
| 审计日志存储满 | 自动轮转归档，保留最近 90 天记录 | N/A |
| 账号被锁定 | 返回 423，提示剩余锁定时间 | 423 |
| 并发登录检测 | 旧会话被踢出时返回 401，提示"账号在其他设备登录" | 401 |

| 维度 | 评测内容 | 权重 |

#### F-12: 安全管控模块

**职责**：全链路安全管控，确保机器人代码的安全性。

**高安全风险模块三级界定标准**：

| 风险等级 | 界定标准 | 管控规则 |
|---------|---------|---------|
| **极高安全风险** | 直接控制急停逻辑、安全防护、故障兜底核心机制 | 强制人工审核，任何核心修改重走全流程校验与重审 |
| **高安全风险** | 运动控制核心逻辑、避障算法、轨迹生成、硬件驱动安全代码 | 强制人工审核，核心修改重走全流程校验与重审 |
| **一般风险** | 运动学解算、传感器预处理、状态估计中安全相关模块 | AI 安全校验 + 自动化测试，发现高风险问题时触发人工审核 |
| **低风险** | 工具函数、数据预处理、辅助脚本 | 本地校验 + 自动化测试，无额外管控 |

**兜底规则**：边界模糊的模块一律按高安全风险模块标记，宁严勿漏。

**安全编码分层校验**：

| 层级 | 校验内容 | 执行主体 |
|------|---------|---------|
| 第一层 | 工具自动校验（Cppcheck/Clang-Tidy/Pylint/Roslint） | 智能体调度平台本地脚本 |
| 第二层 | AST 规则校验（实时循环约束、硬编码检测等） | 智能体调度平台本地脚本 |
| 第三层 | 逻辑校验（安全兜底、边界条件、异常分支） | 算法边界与安全校验 Agent |

**安全编码规范**：

- C++：强制遵循 Google C++ Style Guide + ROS C++ 编码规范
- Python：强制遵循 PEP8 + ROS Python 编码规范
- 禁止使用不安全函数（strcpy/sprintf/gets 等）
- 实时循环禁止动态内存分配、阻塞调用、文件 IO、高频日志
- 运动控制代码必须添加双层极限值约束
- 所有输入数据必须做合法性校验

**审核必查项**：

| 序号 | 检查项 | 不通过处理 |
|------|--------|-----------|
| 1 | 急停逻辑全分支覆盖 | 打回重写，标注缺失分支 |
| 2 | 运动控制极限值约束 | 打回重写，标注缺失约束 |
| 3 | 异常工况兜底机制 | 打回重写，标注缺失场景 |
| 4 | 边界条件处理 | 打回重写，标注缺失边界 |
| 5 | 安全编码规范符合性 | 打回重写，附规范违反清单 |
| 6 | 测试覆盖情况 | 补充测试用例 |

**审核迭代限制**：单个高风险模块审核驳回修改最多 3 次，超过触发架构级评审。

#### F-13: 人工修改检测与重校验模块

**职责**：检测人工对已完成模块的修改，执行分级重校验。

**检测机制**：

- 文件哈希值比对（数据库记录 vs 当前文件，SHA-256）
- 文件修改时间监控（mtime 对比）
- 人工操作日志记录

**分级处理规则**：

| 修改影响等级 | 判定标准 | 处理流程 |
|-------------|---------|---------|
| **无影响** | 仅修改注释、非核心参数 | 仅执行本地静态检查，更新产物状态与哈希值 |
| **轻微影响** | 修改非核心业务逻辑，不涉及接口变更 | 重走「静态检查 → 安全校验 → 单模块测试」全流程 |
| **核心影响** | 修改核心业务逻辑、算法实现、接口定义、安全约束 | 重走全流程校验测试；若涉及接口变更，触发全局接口变更闭环 SOP |
| **高风险模块** | 修改极高/高安全风险模块的任何内容 | 重走全流程 + 强制人工安全审核 |

**批量修改处理**：检测到批量修改多个模块/全局架构文件 → 立即暂停所有未执行任务 → 输出《人工修改影响范围报告》→ 用户确认后逐个处理。

#### F-15: 断点续跑与异常恢复模块

**职责**：任务中断后自动恢复，从最近完成节点重启。

**重启一致性校验**（4 步）：

```
第一步：产物完整性校验
  → 校验数据库状态标记 vs 产物文件存在性 vs 文件哈希值一致性
  → 校验是否通过下游环节校验

第二步：全局信息变更校验
  → 检查全局需求文档、架构设计、接口规范是否被人工修改
  → 有变更 → 完成影响范围全量评估

第三步：依赖链一致性校验
  → 校验已完成任务产物变更是否影响下游任务
  → 上游核心内容变更 → 自动标记下游任务为「待重校验/待更新」

第四步：输出《断点评估报告》
  → 明确已完成任务、待执行任务、变更影响范围、建议执行策略
  → 用户确认后继续执行
```

**断点定位**：以「最近一个 100% 完成、且通过下游环节校验的节点」为起点。

**特殊节点处理**：

| 中断场景 | 处理策略 |
|---------|---------|
| 处于人工确认/审核环节 | 保持等待状态，重新推送确认提醒 |
| 处于熔断暂停状态 | 保持暂停，等待配额恢复或人工指令 |
| Claude Code 会话失效 | 自动创建新会话，从数据库恢复，从断点继续 |

**中断恢复成功率目标**：≥ 95%


### 2.3 全流程 SOP（标准操作流程）

```
[阶段 1] 需求澄清与确认
    输入: 用户模糊需求
    输出: 结构化需求文档
    ↓
[阶段 2] 架构设计
    输入: 结构化需求文档
    输出: 初始架构设计（5 章节）
    ↓
[阶段 3] 架构批判迭代
    输入: 初始架构设计
    输出: 优化后的架构设计 + 缺陷修复记录
    规则: 最多 3 轮迭代
    ↓
[阶段 4] 人工架构确认
    输入: 优化后的架构设计
    输出: 确认的架构设计（或驳回）
    规则: 最多 2 次驳回
    ↓
[阶段 5] 提示词工程
    输入: 确认的架构设计
    输出: 标准化提示词
    ↓
[阶段 6] 任务拆解与分发
    输入: 确认的架构设计 + 标准化提示词
    处理: 拓扑排序循环依赖检测 → 生成 JSON 任务清单 → 任务清单复核 → 前置校验
    输出: 分发至 Claude Code Agent Teams
    ↓
[阶段 7] Agent Teams 协同开发
    输入: JSON 任务清单
    处理: 三级执行策略路由 → 最少负载调度 → 优先执行全局接口任务 → 基于依赖关系有序执行
    输出: 各模块代码产物
    ↓
[阶段 8] 单模块校验
    输入: 代码产物
    处理: 静态检查 → AST 规则校验 → 预编译校验 → 安全校验（高风险模块）
    输出: 校验结果（通过/打回）
    ↓
[阶段 9] 高风险模块人工审核
    输入: 高风险模块代码 + 校验结果
    输出: 审核结果（通过/驳回）
    规则: 强制人工审核，最多 3 次驳回
    ↓
[阶段 10] 单模块测试
    输入: 校验通过的代码
    处理: 单元测试 → 性能测试 → 仿真场景测试 → 故障注入测试
    输出: 测试报告
    ↓
[阶段 11] 全局集成校验
    输入: 全部模块代码
    处理: 接口兼容性校验 → ROS 包规范校验 → 跨模块安全联动校验 → 隐式循环依赖检测
    输出: 集成校验报告
    ↓
[阶段 12] 系统评测
    输入: 集成后的全量代码
    处理: 5 维度全局深度评测（架构/代码质量/算法/安全/工程化）
    输出: 结构化评测报告
    规则: 最多 2 轮迭代
    ↓
[阶段 13] 人工仿真验证
    输入: 评测通过的代码
    处理: 功能测试 → 算法效果验证 → 安全功能专项测试
    输出: 仿真验证报告
    ↓
[阶段 14] 交付归档
    输入: 验证通过的代码
    处理: CHANGELOG 生成 → Git 提交与 Tag 创建 → 交付物归档
    输出: 交付包 + 归档记录
```

### 2.5 数据模型概览

**核心实体关系**：

```
User (用户)
  ├── 1:N → Session (会话)
  │           └── 1:N → Conversation (对话)
  ├── 1:N → Workflow (工作流)
  │           ├── 1:N → Stage (阶段)
  │           └── 1:N → Task (任务)
  │                     ├── 1:N → TaskDependency (任务依赖)
  │                     └── 1:N → Artifact (产物)
  └── 1:N → QuotaRecord (配额记录)

Agent (智能体)
  └── 1:N → Task (任务，执行关系)

Skill (技能)
  └── N:N → Task (任务，复用关系)
```

**核心实体定义**：

| 实体 | 关键字段 | 说明 |
|------|---------|------|
| User | id, username, role(admin/developer/viewer), password_hash, locked_until | 用户，支持 RBAC 三级角色 |
| Session | id, user_id, mode(chat/coding), status, created_at | 用户会话，chat/coding 双模式 |
| Workflow | id, session_id, status(IDLE→...→DELIVERING), current_stage | 工作流，全流程状态机 |
| Task | id, workflow_id, agent_id, type, status(6 states), risk_level, priority, timeout | 原子任务，6 种状态 |
| TaskDependency | task_id, depend_task_id | 任务依赖关系 |
| Artifact | id, task_id, type, file_path, hash, status | 代码产物，含哈希值 |
| QuotaRecord | id, dimension(5h/weekly/monthly), used, total, alert_level | 配额消耗记录 |
| Skill | id, name, embedding(vector), source_task_id, content | 记忆库技能 |
