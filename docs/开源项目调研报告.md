## 第一章：本项目定位

### 1.1 项目概览

**Hermes 智能体调度平台** 是基于 Hermes 内核的 **Web 端 AI 智能体调度平台**，核心定位：

- **双模式**: 日常聊天模式（Hermes 闲聊）+ 编程模式（Claude Code 子代理）
- **Web 优先**: 区别于业界主流的 TUI 终端界面
- **强对话体验**: 豆包风格对话 UI（消息气泡、玻璃拟态、贴底浮动输入区、模式切换）
- **多 Session 历史**: 左侧 Sidebar 折叠 / 展开切换 + 会话搜索 + 标签筛选
- **文件浏览器 / 代码查看器**: 编程模式右侧 VSCode 风格树 + 语法高亮
- **用量监控**: 火山引擎 Coding Plan 5h 10000 次配额 + 实时 token 统计
- **规划视图**: 提示词优化 → 自动规划 → 用户确认 → 按模块分发执行
- **当前版本**: v2.10.4（前端） + 后端 FastAPI

### 1.2 技术栈

- **后端**: FastAPI + SQLAlchemy (Async) + SQLite + Pydantic v2 + uvicorn
- **前端**: React 19 + TypeScript 5.6 + Vite 6 + Tailwind CSS 3.4
- **AI 内核**: Hermes（Nous Research）+ Claude Code CLI（Anthropic 官方）
- **依赖**: httpx 0.28.1 + Subprocess（Node.js sandbox）+ tmux（业界主流）

### 1.3 核心功能矩阵（截至 v2.10.4）

| 功能域 | 现有能力 |
|---|---|
| **会话管理** | 多 Session 历史 + localStorage 持久化 + 模式分组（chat/coding）+ 404 自动回退 |
| **对话体验** | 流式 SSE 响应 + 思考内容折叠 + 消息气泡 hover 工具栏 + 题外话模式（占位）|
| **编程模式** | ProjectSelector（新建/打开项目）+ FileExplorer + CodeViewer + 紧凑聊天布局 |
| **用量监控** | 火山引擎 Coding Plan API + 30 秒缓存 + 后台刷新 + 404 告警抑制 |
| **UI 美化** | 豆包风格 + 玻璃拟态 + 贴底浮动输入区 + 暖色 + 大圆角 + 字体排版规范 |
| **持久化** | ORM 模型 + ALTER TABLE 迁移 + legacy-default 兜底 |

## 第三章：17 个核心开源项目详尽分析

### 3.1 Composio Agent Orchestrator

#### 基础信息

- **GitHub**: [ComposioHQ/agent-orchestrator](https://github.com/ComposioHQ/agent-orchestrator)（已从 ComposioHQ 转移至 [AgentWrapper](https://github.com/AgentWrapper) 独立维护，原地址仍可用）
- **最新版本**: v0.9.3 (nightly) + 48 个历史版本
- **许可证**: MIT
- **安装包**: `@aoagents/ao` (npm) / `@aoagents/ao@nightly`
- **代码量**: 1,274 commits + 14,358 commits（合并 monorepo）/ 49 个 packages
- **仪表板**: `http://localhost:3000`
- **测试覆盖**: 3,288 test cases

#### 定位

> "Agent-agnostic + Runtime-agnostic + Tracker-agnostic" — AI 编程代理的**编排层**，每个 agent 独立 git worktree + branch + PR，CI 失败自动重试，review 评论自动处理。

#### 解决的核心用户痛点

1. **单代理局限**: 一个任务让 Claude Code 跑着，另一个任务只能干等
2. **多代理环境冲突**: 多个代理同时改同一仓库，git 冲突反复出现
3. **架构设计 ↔ 代码生成交接**: 两个 agent 没法"交接"
4. **团队无共享状态**: 每个人单独跑代理，没有共享状态也没法互相看进度
5. **CI 失败无人接管**: 自动化流程断裂需要人工转发

#### 核心功能

| 模块 | 能力 | 我方实现 |
|---|---|---|
| **Git Worktree 隔离** | 每个 agent 独立 worktree + branch + PR | ❌ 单 workspace |
| **CI 自动重试** | agent 自己读日志、修代码、retry 2 次 | ❌ 无 |
| **Web Dashboard** | Kanban 视图按状态分组（failing CI / awaiting review / running fine）| ⚠️ 简易 |
| **Reaction 系统** | 监听 GitHub Events，自动 send-to-agent / notify / escalate | ❌ 无 |
| **7 个 Plugin Slot** | Runtime / Agent / Workspace / Tracker / SCM / Notifier / Terminal | ❌ 1 个（Claude Code only）|
| **macOS 远端访问** | caffeinate 防睡眠 | ❌ |
| **多 agent 平台** | Claude Code / Codex / Aider / Cursor / OpenCode / Kimicode | ❌ Claude Code only |
| **多 runtime** | tmux (mac/Linux) / process/ConPTY (Windows) / Docker | ❌ |
| **多 tracker** | GitHub / Linear / GitLab | ❌ |
| **多 notifier** | desktop / slack / discord / composio / webhook / openclaw | ❌ |

#### Plugin 架构

```yaml
# agent-orchestrator.yaml
$schema: https://raw.githubusercontent.com/ComposioHQ/agent-orchestrator/main/schema/config.schema.json
port: 3000

defaults:
  runtime: tmux
  agent: claude-code
  workspace: worktree
  notifiers: [desktop]

projects:
  my-app:
    repo: owner/my-app
    path: ~/my-app
    defaultBranch: main
    sessionPrefix: app

reactions:
  ci-failed:
    auto: true
    action: send-to-agent
    retries: 2
  changes-requested:
    auto: true
    action: send-to-agent
    escalateAfter: 30m
  approved-and-green:
    auto: false
    action: notify
```

#### 深度补充：7 个 Plugin Slot 详解

Composio AO 的插件化架构是其核心竞争力，每个 slot 均可独立替换：

| Plugin Slot | 作用 | 内置实现 |
|---|---|---|
| **Runtime** | 代理运行环境（终端/进程管理） | tmux (mac/Linux)、process/ConPTY (Windows)、Docker |
| **Agent** | 代理内核（编程代理） | Claude Code、Codex、Aider、Cursor、OpenCode、Kimicode |
| **Workspace** | 工作空间隔离策略 | Git worktree（每个 agent 独立 branch + worktree） |
| **Tracker** | 任务跟踪与项目管理 | GitHub Issues/PRs、Linear、GitLab |
| **SCM** | 源码管理与版本控制 | GitHub、GitLab |
| **Notifier** | 通知渠道 | desktop、Slack、Discord、Composio、Webhook、OpenClaw |
| **Terminal** | 终端抽象层 | tmux pane、process spawn、ConPTY |

#### 深度补充：16 个 Session 状态机（据项目文档）

Composio AO 维护了完整的 session 状态机（据项目文档共 16 个状态），覆盖代理从创建到销毁的全生命周期：

```
CREATED → INITIALIZING → RUNNING → (PAUSED / WAITING_FOR_REVIEW / 
WAITING_FOR_CI / FAILED / COMPLETED) → ARCHIVED
```

关键状态转换：
- `RUNNING → WAITING_FOR_CI`: CI 失败自动触发 retry（最多 2 次）
- `RUNNING → WAITING_FOR_REVIEW`: PR 创建后等待人工 review
- `WAITING_FOR_REVIEW → RUNNING`: review 评论自动 send-to-agent 修复
- `FAILED → RUNNING`: 支持手动 resume 重试

#### 深度补充：Reaction 系统（据项目文档，25+ 事件类型）

Reaction 系统是 Composio AO 的自动化引擎，据项目文档监听 25+ 种 GitHub/Linear 事件并自动响应：

| 事件类型 | 触发条件 | 默认动作 | 可配置 |
|---|---|---|---|
| `ci-failed` | CI pipeline 失败 | send-to-agent（自动修复） | retries: 2 |
| `ci-passed` | CI 通过 | notify | — |
| `changes-requested` | PR review 要求修改 | send-to-agent | escalateAfter: 30m |
| `approved-and-green` | review 通过 + CI 绿 | notify（提示可 merge） | auto: false |
| `pr-merged` | PR 已合并 | cleanup worktree | — |
| `pr-closed` | PR 关闭（未合并） | archive session | — |
| `agent-crashed` | 代理进程崩溃 | restart + notify | maxRestarts: 3 |
| `agent-timeout` | 代理超时无响应 | kill + notify | timeout: 30m |

#### 深度补充：自改进系统

Composio AO 项目本身使用自己的多代理系统进行开发，据项目方自述 agent 已经为项目贡献了 **40,000 行 TypeScript 代码**，形成"用 AO 开发 AO"的自举循环。2026 年项目已从 ComposioHQ 组织转移到 **AgentWrapper**（由 Prateek Karnal 维护）独立维护，标志着从企业附属项目到社区独立项目的转变，原 ComposioHQ 地址仍可用。

#### 我方核心差距

- **真正并行**: 我方每次只能跑一个 Claude Code 实例
- **PR 自动化**: 我方手动 git push / 创建 PR
- **CI 反馈闭环**: 我方无 CI 集成
- **多 agent 平台**: 我方只能 Claude Code，不能 codex/aider/ollama

#### 解决的"额外"用户需求

1. **"CI 失败自动修复"** — 我方用户没想到但确实痛：CI 挂了 agent 自己修
2. **"review 评论自动处理"** — review 提的 comment agent 自己改
3. **"全自动化 PR 生命周期"** — PR 创建 → CI → review → merge 全自动
4. **"Web Dashboard 远端监控"** — Mac 合盖也能查看 agent 进度

#### 借鉴 ROI

- **实现难度**: 🔴 高（需 git worktree + 7 个 plugin slot + reaction 系统 + Web Dashboard 重构）
- **用户价值**: 🔴 极高（直击"单实例串行"最大痛点）
- **建议**: 阶段 1 优先（Task A-D）

### 3.2 Claude Squad

#### 基础信息

- **GitHub**: [smtg-ai/claude-squad](https://github.com/smtg-ai/claude-squad)
- **最新版本**: v1.0.18 (2026-05-19)
- **许可证**: AGPL-3.0（注意：传染性强，**不兼容**我方 MIT/Apache）
- **语言**: Go 为主
- **安装**: `brew install claude-squad` 或 `curl -fsSL ... | bash`
- **命令名**: `cs`（也支持自定义名称）

#### 定位

> 终端应用管理多个 Claude Code / Codex / Gemini / Aider 在独立 workspace 中并行

#### 解决的核心用户痛点

1. 想同时跑多个 AI 编程任务（一个写后端、一个改 bug、一个重构）
2. 不想在多个终端窗口间切换
3. 想集中查看所有 instance 状态 + diff

#### 核心功能

| 模块 | 能力 | 我方实现 |
|---|---|---|
| **TUI 终端界面** | 上下方向键 (j/k) 在 instance 间导航 | ❌ Web only |
| **tmux 隔离 session** | 每个 agent 独立 tmux session | ❌ |
| **Git worktree 隔离** | 每个 task 独立 worktree | ❌ |
| **Agent profile 系统** | `claude` / `codex` / `aider` 启动命令配置 | ❌ |
| **yolo / autoyes 模式** | `-y` flag 自动接受所有提示 | ❌ |
| **review 工作流** | `s` commit+push, `c` checkout, `r` resume, `?` help | ❌ |
| **Shift+J/K 重排序** | instance 重排序 | ❌ |
| **preview / diff tab 切换** | `tab` 键在两个 tab 间切换 | ❌ |
| **多 agent 支持** | Claude Code / Codex / Gemini / Aider | ❌ Claude Code only |

#### 深度补充：TUI 快捷键完整菜单

Claude Squad 的 TUI 界面提供了完整的键盘快捷键体系，所有操作无需鼠标：

```
实例/会话管理:
  n   - 创建新会话
  N   - 创建新会话并附带提示词
  D   - 终止（删除）选中的会话
  ↑/j, ↓/k - 在会话间导航

操作:
  ↵/o     - 附加到选中会话以重新提示
  ctrl-q  - 从会话中分离
  s       - 提交并推送分支到 GitHub
  c       - Checkout：提交更改并暂停会话
  r       - 恢复已暂停的会话
  ?       - 显示帮助菜单

导航:
  tab         - 在预览标签和差异标签之间切换
  q           - 退出应用程序
  shift-↓/↑   - 在差异视图中滚动
```

#### 深度补充：Agent Profile 系统详解

Claude Squad 通过 profile 系统实现多代理平台的统一管理，每个 profile 定义了启动命令和默认参数：

```yaml
# ~/.claude-squad/config.json
profiles:
  claude:
    command: claude
    args: ["--dangerously-skip-permissions"]
    default: true
  codex:
    command: codex
    args: ["exec", "--full-auto"]
  aider:
    command: aider
    args: ["--model", "sonnet", "--no-auto-commits"]
  gemini:
    command: gemini
    args: ["--model", "gemini-2.5-pro"]
```

#### 深度补充：原子 Git Commit 设计

Aider 的核心设计哲学是"每次变更一个原子 commit"，每个 AI 编辑操作自动生成独立的 Git commit，commit message 由 AI 智能生成，清晰描述变更内容。这使得：
- 每次变更可独立 review
- 出问题可精确 revert 到任意一步
- Git history 本身就是完整的开发日志

| **Editor** | AI 直接编辑代码，用户实时审查 | 日常编码、bug 修复 |

#### 深度补充：Repo Map 代码库映射机制

Aider 的 **Repo Map** 是其核心竞争力之一——自动分析整个代码库结构，生成精简的代码库映射图（包含关键函数签名、类定义、模块依赖关系），并将其注入到 LLM 上下文中。这使得 AI 在编辑单个文件时仍能理解全局代码结构，大幅提升跨文件编辑的准确性。

#### 深度补充：Watch 模式（AI! 和 AI? 注释）

Aider 的 Watch 模式允许用户在代码中通过特殊注释与 AI 交互：
- `# AI!` 注释：触发 AI 自动执行该行指示的任务
- `# AI?` 注释：触发 AI 回答该行提出的问题

这种"代码即对话"的交互方式将 AI 深度嵌入开发工作流，无需切换上下文。

#### 深度补充：语音编码（Voice-to-Code）

Aider 内置语音编码功能，支持通过语音输入编写代码。用户口述需求，AI 自动转化为代码编辑操作。这一功能对行动不便的开发者或偏好语音交互的用户极具价值。

#### 深度补充：自动 Lint + Test 循环

Aider 实现了业界领先的自动质量保障循环：
1. AI 编辑代码 → 自动运行 linter 检查
2. 发现 lint 错误 → AI 自动修复
3. 自动运行相关测试用例
4. 测试失败 → AI 分析失败原因并修复
5. 循环直到 lint + test 全部通过

这个闭环机制大幅减少了"AI 写出的代码不能跑"的问题。

#### 深度补充：支持 70+ 模型

Aider 支持超过 70 种 LLM 模型，包括 Claude、GPT、Gemini、DeepSeek、Llama、Qwen、Mistral 等全系列模型，以及通过 OpenAI 兼容 API 接入的任意第三方模型。

- **用户价值**: 🟡 中（git 自动 commit 高价值）

| **可调试性** | YAML 可 diff/review | 难以调试 |
| **灵活性** | 受限于预定义规则 | 高度灵活 |

#### @agent-name 路由机制

Agentrooms 的核心设计是极简路由——用户通过 `@agent-name` 直接指定目标代理，无需 LLM 做路由决策：
- 零编排开销：不消耗 token 做路由
- 确定性：用户明确知道任务发给哪个代理
- 低延迟：直接转发，无 LLM 推理延迟

#### 我方核心差距

- **无远程代理支持**: 我方仅本地执行
- **无 @mention 路由**: 我方无代理间直接通信
- **无动态代理管理**: 我方代理配置静态

#### 解决的"额外"用户需求

1. **"分布式执行"** — 代理可在多台机器上并行运行
2. **"Web 可视化管理"** — 图形界面动态管理代理池
3. **"零成本编排"** — 编排器免费，不消耗 API 配额

#### 借鉴 ROI

- **实现难度**: 🟢 低（@mention 路由 + Web UI 代理管理相对简单）
- **用户价值**: 🟡 中（对多机器用户有价值，对单机用户价值有限）
