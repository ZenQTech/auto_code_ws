# AGV 多车协同调度与安全协同平台 —— 架构评审报告

> 评审版本：v2.0（最终版）
> 评审日期：2026-07-01
> 评审人：批判反思智能体（架构风险官与合规专家）

---

## 一、评审综述

本文档对 `final_architecture_design.md v2.0` 从安全性、实时性、可扩展性、可测试性、兼容性、成本/复杂度 6 个维度进行全维度批判评审。

**总体评估**：架构在模块划分、接口规范、安全设计思路方面表现完整，但仍存在 **8 项高风险、7 项中风险、4 项低风险** 问题。其中最严重的问题集中在 SIL2 合规性论证缺失、WiFi 实时性未分析、单点故障无热备实现方案三个方面。

---

## 二、逐维度评审

### 维度 1：安全性（Safety）— SIL2 合规性审查

#### 🔴 RISK-01：双路急停缺乏真正的硬件异构冗余（高风险）

**问题描述**：
文档声称 "双路独立急停"，但路径 A（`safety_guard` 节点）和路径 B（`agv_{N}_safety_monitor` 节点）均为运行在 Jetson Orin 上的软件节点，共享同一 CPU、同一操作系统、同一 DDS 栈。对于 SIL2 认证，这不符合"硬件故障容错"要求——如果 Jetson Orin 发生系统级故障（内核 panic、DDS 守护进程崩溃、电源故障），两路急停同时失效。

**影响范围**：所有 AGV 的安全关键路径
**根因**：SIL2 要求硬件多样性（diverse hardware），即两路急停应运行在独立硬件上（如一个在 Jetson Orin，另一个在独立的 SIL2 认证安全 PLC）
**修复建议**：
1. 将 B 路从软件节点改为独立的 SIL2 安全 PLC 硬件实现，直接读取传感器（至少 LiDAR 安全区信号），独立于 Jetson Orin 发出急停指令
2. 若成本受限，至少需要独立的安全协处理器（如 Infineon TC2xx 系列）运行 B 路逻辑
3. 在仿真环境中，B 路应模拟独立硬件的行为（增加独立的故障注入通道）

#### 🔴 RISK-02：SIL2 安全论证文档和 FMEDA 分析完全缺失（高风险）

**问题描述**：
文档第 9 节虽然列出了安全关键模块，但完全没有提供以下 SIL2 认证必需的分析：
- FMEDA（故障模式、影响与诊断分析）
- 安全完整性要求的 PFH（每小时危险失效概率）量化目标
- 安全功能的安全状态定义
- 诊断覆盖率（DC）指标
- 共因失效（CCF）分析

**影响范围**：SIL2 合规性不可论证
**根因**：架构设计阶段未纳入 SIL2 认证工程师参与
**修复建议**：
1. 新增 `docs/safety_case.md`，包含完整的 SIL2 安全论证
2. 对每个安全功能（急停、速度限幅、碰撞检测）完成 FMEDA
3. 明确 SIL2 的 PFH 目标值（< 10⁻⁷ / 小时）和诊断覆盖率要求（≥ 90%）

#### 🔴 RISK-03：DDS 分区隔离不能替代物理隔离（中风险）

**问题描述**：
文档 9.4.2 节使用 DDS Partition 机制隔离安全与非安全数据。但 DDS 分区是"逻辑隔离"，所有数据仍在同一 DDS Domain（Domain ID: 10）中传输，共享同一个 Fast-DDS 进程。这意味着：
- Fast-DDS 的 Bug 可能导致安全数据泄露或被非安全节点篡改
- DDS 的 QoS 配置无法阻止非安全节点订阅安全 Topic（ROS2 默认无 Topic 访问控制）
- 没有实现 DDS Security（ROS2 Security enclaves）来实施访问控制

**影响范围**：安全通信层
**修复建议**：
1. 实施 ROS2 Security（SROS2）的访问控制策略，明确安全 Topic 的读写权限
2. 或者将安全节点部署在独立的 DDS Domain（Domain ID: 11），通过网关桥接
3. 在仿真中增加安全通信完整性测试场景

#### 🟡 RISK-04：安全代码约束中的虚函数禁止与 C++ 设计冲突（中风险）

**问题描述**：
文档 9.6 节规定安全代码禁止虚函数调用。但 `safety_guard` 节点是用 C++ 编写的，而：
- ROS2 节点类本身继承自 `rclcpp::Node`，包含虚函数
- 如果使用 pluginlib 加载算法（如碰撞检测器），必然涉及虚函数
- 禁止虚函数意味着无法使用多态设计，限制了代码复用

**影响范围**：safety_guard 节点的 C++ 实现
**修复建议**：
1. 修正为"实时循环 100Hz 路径内禁止虚函数调用"，而非全局禁止
2. 安全节点的初始化阶段允许虚函数调用（非实时路径）
3. 明确区分"实时路径代码"和"非实时配置代码"的约束差异

### 维度 2：实时性（Real-time）

#### 🔴 RISK-05：WiFi 5/6 上 100Hz 控制回路的确定性未分析（高风险）

**问题描述**：
文档 4.3 节规定所有 AGV 通过 WiFi 5/6 与中心服务器通信，中心服务器到车载端的指令频率声称可达 100Hz。但：
- WiFi 是共享介质，存在 CSMA/CA 冲突避免机制，延迟抖动（jitter）通常在 5-50ms 范围
- 10 台 AGV 同时以 100Hz 发送数据时，WiFi 碰撞概率显著增加
- 没有任何最坏情况延迟（Worst-Case Latency）分析
- 没有考虑 WiFi 信道干扰（仓库环境中可能有其他 WiFi 设备、金属货架导致多径衰落）

**影响范围**：所有依赖 WiFi 通信的实时控制指令
**根因**：架构设计中未将网络通信延迟纳入实时性预算
**修复建议**：
1. 补充一份"端到端延迟预算分析"，明确每个环节的延迟分配（传感器 → 感知 → 规划 → 控制 → 通信 → 执行）
2. 对 WiFi 环境进行实测或仿真建模，量化最坏情况延迟
3. 考虑有线网络（工业以太网）用于实时控制通道，WiFi 仅用于非实时状态监控
4. 在仿真中增加网络延迟/丢包模拟测试

#### 🔴 RISK-06：TEB 规划器在 Jetson Orin 上 ≤10ms 的声明缺乏依据（高风险）

**问题描述**：
文档声称 local_planner 的 TEB 规划器能在 ≤10ms（100Hz）内完成。但实际 TEB 规划器的计算时间受以下因素影响：
- TEB 使用非线性优化求解（g2o/ceres），优化迭代次数不确定
- 动态障碍物数量增加时，约束条件增多，求解时间非线性增长
- Jetson Orin 的 GPU 不能加速非线性优化（CPU-bound 任务）
- 已知 TEB 在类似硬件上典型运行时间为 20-50ms（含碰撞检测）

**影响范围**：local_planner 的实时性保证
**修复建议**：
1. 在 Jetson Orin（或同等硬件）上做 TEB 基准测试，获取实际运行时间分布
2. 设置 TEB 的 max_iterations 上限，超时则使用上一周期的解（牺牲最优性保实时）
3. 预留 DWA 作为轻量级回退方案（DWA 通常可在 5-10ms 完成）
4. 明确声明 "TEB 100Hz 目标，DWA 保底 100Hz 保证"

#### 🟡 RISK-07：100Hz 急停响应时间与 100ms 看门狗超时不一致（中风险）

**问题描述**：
文档 9.7 节的急停触发源矩阵中，通信中断的检测延迟标注为 ≤100ms（看门狗超时），但安全关键路径总延迟要求 ≤10ms。这意味着：
- 通信中断后的 0-100ms 内，AGV 不会触发急停
- 在这 100ms 内，以 1.5m/s 速度行驶的 AGV 可能前进 150mm，超出了安全距离预算

**影响范围**：通信中断场景下的安全
**修复建议**：
1. 降低看门狗超时到 50ms（需要平衡网络抖动和安全性）
2. 或者增加"心跳丢失预测"机制：连续丢失 2 个预期心跳即触发预减速（非急停）

### 维度 3：可扩展性（Scalability）

#### 🔴 RISK-08：中心服务器是系统级单点故障，热备方案未设计（高风险）

**问题描述**：
文档 8.5 节承认"单点故障→热备解决"，但：
- 架构中没有任何热备机制的设计（没有主备切换逻辑、没有状态同步、没有故障检测）
- 中心服务器故障时，task_manager、traffic_controller、fleet_safety_monitor 同时失效
- 没有说明 AGV 在中心服务器故障时的行为（自主降级运行？还是全部急停？）

**影响范围**：全系统可用性
**修复建议**：
1. 设计主备中心服务器架构（active-passive），通过 etcd/Redis 同步关键状态
2. 定义"中心失联"模式下 AGV 的行为：保留最后分配的路径，降级为分布式死锁避免
3. 在仿真中增加"中心服务器故障恢复"测试场景

#### 🟡 RISK-09：10 台 AGV 在单一 DDS Domain 上的通信压力未评估（中风险）

**问题描述**：
10 台 AGV × 每个 Topic 的发布频率累加：
- scan: 10 × 30Hz = 300 msg/s
- imu: 10 × 100Hz = 1000 msg/s
- odom_fused: 10 × 50Hz = 500 msg/s
- safety_state: 10 × 100Hz = 1000 msg/s
- heartbeat: 10 × 10Hz = 100 msg/s
- cmd_vel: 10 × 100Hz = 1000 msg/s
- 其他... 总计约 4000+ msg/s

加上 WiFi 带宽限制（通常实际吞吐量 ~200-400 Mbps），以及 DDS 的发现协议（Discovery）在节点增加时的 O(N²) 通信量，10 台 AGV 时 DDS 发现风暴是一个已知风险。

**影响范围**：扩展到 10 台 AGV 时的通信稳定性
**修复建议**：
1. 进行 DDS 通信带宽估算（消息大小 × 频率 × AGV 数量）
2. 使用 DDS 分区减少无关消息的传输
3. 考虑使用 ROS2 的 topic_statistics 监控实际带宽
4. 对 Discovery Phase 使用 Fast DDS 的静态发现机制减少风暴

#### 🟢 RISK-10：拍卖算法 O(N²) 对 10 台足够但对 20 台可能不足（低风险）

**问题描述**：
文档指出拍卖算法复杂度 O(N²) 对 10 台 AGV 完全可行。但如果未来扩展到 20 台，O(N²) 变为 4 倍计算量。不过由于当前需求仅到 10 台，此风险较低。

**修复建议**：
在任务调度器接口设计中预留"调度算法插件化"的扩展点，未来可替换为匈牙利算法或基于约束的调度。

### 维度 4：可测试性（Testability）

#### 🔴 RISK-11：SIL2 安全论证测试未设计故障注入框架（高风险）

**问题描述**：
文档 12.3 节的测试场景矩阵包含 12 个场景，但没有：
- 故障注入测试的设计（Fault Injection Testing）
- 安全功能的 MC/DC（修正条件/判定覆盖）测试要求
- SIL2 要求的"每个安全功能至少 2 个故障注入测试用例"

SIL2 认证要求对每个安全功能进行故障注入测试，验证其在故障条件下的行为。例如：急停按钮故障、传感器数据损坏、通信链路中断、内存错误等。

**影响范围**：SIL2 认证测试
**修复建议**：
1. 新增"故障注入测试"章节，为每个安全功能设计至少 2 个故障注入测试用例
2. 使用 ROS2 的 fault_injection 机制或 Gazebo 的故障模拟插件
3. 定义测试覆盖率的量化目标（语句覆盖 ≥ 100%，MC/DC ≥ 100% 对安全关键代码）

#### 🟡 RISK-12：50 组仿真场景未明确安全边界覆盖（中风险）

**问题描述**：
文档提到 50 组仿真场景，但未说明：
- 哪些场景覆盖了安全边界条件（如：障碍物恰好出现在 0.8m 安全边界处）
- 哪些场景覆盖了传感器退化情况（LiDAR 降级到 10Hz、IMU 噪声增大 10x）
- 场景的自动化运行和通过/失败判定标准
- 边界值分析（BVA）和等价类划分（ECP）是否已完成

**修复建议**：
1. 建立安全边界覆盖矩阵，确保每个安全触发条件在边界值 ±10% 范围内至少有一个测试用例
2. 增加传感器退化场景（LiDAR 丢失 50% 点云、IMU 漂移增大）
3. 所有测试场景应可自动化运行，并有明确的 PASS/FAIL 判定逻辑

#### 🟢 RISK-13：无性能基准测试框架（低风险）

**问题描述**：
文档 12.2 节列出了性能指标，但没有定义：
- 性能测试的基线环境（硬件配置、网络环境）
- 性能测试的自动化框架
- 性能退化预警阈值

**修复建议**：
1. 在 CI 中集成性能回归测试
2. 为每个关键指标定义"预警阈值"（如：TEB 规划时间 > 15ms 标记为警告）

### 维度 5：兼容性（Compatibility）

#### 🟡 RISK-14：ros_gz_bridge 对自定义消息类型的支持可能不完整（中风险）

**问题描述**：
文档 6.4 节定义了大量自定义消息类型（`agv_msgs/SafetyStatus`、`agv_msgs/EmergencyStatus` 等）。ros_gz_bridge 的桥接能力：
- ros_gz_bridge 默认只支持标准消息类型的桥接（LaserScan、IMU、Odometry 等）
- 自定义消息类型需要编写额外的 bridge 插件（C++ 代码）
- 文档没有提及自定义消息在 Gazebo ↔ ROS2 之间的桥接方案

**影响范围**：仿真环境中安全状态/急停指令的桥接
**修复建议**：
1. 列出需要桥接的自定义消息类型，评估是否需要自定义 bridge 插件
2. 对于安全相关消息（SafetyStatus、EmergencyStatus），考虑使用 ROS2 Service 代替 Topic 进行桥接（Service 不需要 bridge 插件）
3. 在仿真中验证所有自定义消息的端到端通信

#### 🟡 RISK-15：ROS2 Humble + Gazebo Ignition Fortress 的已知兼容性问题（中风险）

**问题描述**：
ROS2 Humble 官方推荐的仿真版本是 Gazebo Ignition Fortress，但存在已知问题：
- Fortress 的 ign-transport 版本与 Humble 的 ROS2 通信栈存在版本兼容性风险
- 部分传感器插件（如 RgbdCamera）在 Fortress 中表现不稳定
- ros_gz_bridge 的不同版本对消息类型映射的支持不一致

**修复建议**：
1. 在开发初期先验证核心传感器（LiDAR + IMU + DiffDrive）的桥接是否正常工作
2. 准备回退方案：如果 Fortress 兼容性问题严重，考虑使用 Gazebo Classic 11（仍与 Humble 兼容）
3. 锁定 ros_gz_bridge 的具体版本号，避免自动升级导致的兼容性问题

#### 🟢 RISK-16：Python 节点的 ROS2 GIL 问题（低风险）

**问题描述**：
api_gateway 和 web_bridge 使用 Python 3.10 实现。ROS2 Python 客户端（rclpy）受 GIL（全局解释器锁）限制，在高并发场景下（100 并发请求）可能出现回调延迟。

**影响范围**：API 网关的并发性能
**修复建议**：
1. 使用 asyncio 或多进程模式绕过 GIL 限制
2. 或考虑将高频 API 迁移到 C++ 实现

### 维度 6：成本/复杂度（Cost/Complexity）

#### 🟡 RISK-17：19 个节点在 3-5 台 AGV 场景下是过度设计（中风险）

**问题描述**：
当前需求为 3-5 台 AGV，但架构设计了 19 个节点（中心 8 个 + 车载 9 个 + 仿真 2+ 个）。在 3 台 AGV 场景下，实际运行约 8 + 3×9 = 35 个进程。

过度设计的表现：
- `charge_scheduler` 作为一个独立节点仅运行 1Hz 更新，可以合入 task_manager
- `web_bridge` 和 `api_gateway` 可以合并（FastAPI 本身支持 WebSocket）
- `sensor_fusion` 功能可以合入 `localization` 节点（减少进程间通信开销）
- `fleet_monitor` 和 `fleet_safety_monitor` 的部分监控功能重叠

**修复建议**：
1. 合并 charge_scheduler → task_manager（作为一个模块而非独立节点）
2. 合并 web_bridge → api_gateway（FastAPI 原生支持 WebSocket）
3. 考虑合并 sensor_fusion → localization（减少通信延迟）
4. 对于 3-5 台场景，目标节点数可优化到 12-14 个

#### 🟡 RISK-18：Python/C++ 混用增加维护成本（中风险）

**问题描述**：
架构中实时模块用 C++17，非实时模块用 Python 3.10。混用的具体成本：
- 团队成员需要同时掌握 C++ 和 Python 的 ROS2 开发
- Python 节点的接口与 C++ 节点接口需要保持完全一致（消息类型、QoS 配置）
- 单元测试需要两套框架（C++ 用 GTest，Python 用 pytest）
- CI 流水线需要配置两种编译/测试环境

**修复建议**：
1. 如果团队以 Python 为主，考虑将非实时 C++ 节点（fleet_monitor、map_server）也改为 Python
2. 如果团队以 C++ 为主，考虑将 Python 节点（api_gateway、web_bridge）改为 C++ 的 drogon/drogon 框架
3. 至少统一测试框架（Python 节点的测试也通过 ROS2 launch 测试统一管理）

#### 🟢 RISK-19：TEB 参数调优工作量被低估（低风险）

**问题描述**：
TEB 规划器有约 30+ 可调参数（权重系数、约束松弛、优化迭代次数等），在 25m×20m 的仓库环境中：
- 不同区域的通道宽度不同（主通道 3m vs 副通道 2m）
- 不同 AGV 的载荷不同（空载 vs 500kg 满载影响动力学参数）
- TEB 参数对场景变化敏感，需要大量的调优工作

**修复建议**：
1. 使用自动化参数调优工具（如 ROS2 的 parameter_tuning 或 Bayesian optimization）
2. 在仿真中设计参数扫描测试（parameter sweep）
3. 考虑从 TEB 切换到更适合结构化环境的 Navigation2 的 MPPI 控制器（模型预测路径积分）

## 五、优先级行动建议

### 必须立即处理（P0 — 阻塞开发）

1. **RISK-01 + RISK-02（安全性）**：在进入开发前，必须完成 SIL2 安全架构的重新设计，明确双路急停的硬件异构方案，启动 FMEDA 分析。这是硬性约束，不可绕过。

2. **RISK-05 + RISK-06（实时性）**：在进入编码前，必须完成端到端延迟预算分析和 TEB 在目标硬件上的基准测试。如果 100Hz 在 WiFi + Jetson Orin 上不可达，需要立即调整架构。

3. **RISK-08（可扩展性）**：中心服务器热备方案必须在第一版迭代中完成设计，否则系统在单点故障时完全不可用。

### 应在 Phase 1 中处理（P1）

4. **RISK-11（可测试性）**：故障注入测试框架是 SIL2 验证的前提，应在 Phase 1 仿真阶段完成设计。

5. **RISK-17（成本/复杂度）**：在开发开始前完成节点合并优化，可减少 30-40% 的开发工作量。

6. **RISK-14 + RISK-15（兼容性）**：在 Phase 1 初期验证 ROS2 Humble + Fortress + ros_gz_bridge 的技术可行性，避免后期发现不可逾越的技术障碍。

### 可在 Phase 2/3 中处理（P2）

7. RISK-03、RISK-04、RISK-07、RISK-09、RISK-12、RISK-18
8. RISK-10、RISK-13、RISK-16、RISK-19

## 六、对架构的正面肯定

在批评之余，也需指出架构设计的亮点：

1. **接口规范完整**：24 个 Topic、15 个 Service、5 个 Action 的定义清晰完整，自定义消息类型设计合理，覆盖了所有关键通信场景。

2. **安全设计思路正确**：三层速度限幅、双路急停仲裁器（OR 逻辑）、安全代码约束等设计思路符合安全工程最佳实践。

3. **分层架构合理**：应用层 → 业务层 → 算法层 → HAL 层的 4 层架构划分清晰，关注点分离做得好。

4. **仿真-真实复用策略明确**：核心算法层 100% 复用、HAL 层接口统一、launch 参数切换，是一个务实的方案。

5. **文档质量高**：冲突修正记录详细、架构图完整、参数与需求文档严格对齐。

## 七、结论

**评审结论：有条件通过，需在进入开发前完成 3 项 P0 风险项的整改。**
